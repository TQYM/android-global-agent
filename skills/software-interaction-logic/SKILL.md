# 软件交互逻辑（Software Interaction Logic）

## 0. 如何使用本 Skill

1. **执行手机任务前**：通读 §2–§8，把决策纪律带入每一步动作选择；特别注意 §7 敏感红线与 §7.5 能力边界——**模型侧纪律是主防线**。
2. **改动交互逻辑前**：先读 §1 适用范围与溯源指针，再按 §8 检查清单自审，最后对照规范守则走变更流程。
3. 本 Skill 与引擎 `SCHEMA` 常量保持逐条对应；两者冲突时**以代码为准并立即回改本文档**（见 §9 溯源）。

**规范性用语**（RFC 2119 语义）：**必须**（MUST，违反即缺陷）、**必须不 / 禁止 / 绝不**（MUST NOT，同义强化用法）、**应**（SHOULD，偏离需给出书面理由）、**可以**（MAY，真正可选）。

## 1. 目的与适用范围

### 1.1 目的

为「自然语言任务 → 可验证手机操作」的闭环提供**确定性交互纪律**，使任意模型在任意 ROM 上产出：

- **可预期**：同样的屏幕状态与任务语境，收敛到同样的动作选择；
- **可验证**：每步动作后以屏幕变化复验，终态必须自证（done 摘要 / fail 归因）；
- **可中断**：任何时刻用户可停；敏感场景模型必须主动确认，引擎守卫为部分覆盖的辅助（§7）。

### 1.2 适用

- AgentLite 引擎驱动的手机自动化任务执行（决策侧）；
- 动作词表、降级链、循环治理、终态语义的设计与评审（工程侧）；
- 交互类缺陷（卡死、重复、误触、越权）的定位与修复。

### 1.3 不适用

- Android 应用自身 UI 实现（见 `android-compose-ui` 等）；
- 无屏幕感知的纯 API 自动化；
- Root 完整版 `agent-client/` 的虚拟屏沙盒逻辑（其安全模型另文约束）。

## 2. 交互主循环（核心模型）

```text
┌─────────────────────────────────────────────────────┐
│  用户任务（可选：规划模型先产出 目标/步骤/完成判据/风险） │
└───────────────────────┬─────────────────────────────┘
                        ▼
        ┌────── ① 感知 PERCEIVE ──────┐
        │ 无障碍节点表（上限 25 节点，   │
        │ clickable 按 y 坐标前置重排） │
        │ + 屏幕截图 + 屏幕形态         │
        └───────────────┬─────────────┘
                        ▼
        ┌────── ② 决策 DECIDE ────────┐
        │ 先判敏感守卫与环境态（§3/§7）；│
        │ 按 §4 分层从高到低选动作；    │
        │ 每步只输出 1 个 JSON 动作     │
        └───────────────┬─────────────┘
                        ▼
        ┌────── ③ 执行 ACT ───────────┐
        │ 引擎按降级链执行（§5）；       │
        │ 失败回报进上下文，不静默       │
        └───────────────┬─────────────┘
                        ▼
        ┌────── ④ 复验 VERIFY ────────┐
        │ waitForChange 自适应等待：    │
        │ 前置 60ms + 80ms 轮询，       │
        │ 上限 600ms；无变化 → §6 治理  │
        └───────────────┬─────────────┘
                ▼                     ▼
        满足完成判据 → done      无法满足 → fail（带归因）
```

**不变量（I-1 ~ I-4）**：

| 编号 | 不变量 | 违反后果 |
|---|---|---|
| I-1 | 每轮**必须**只输出一个 JSON 动作对象，无任何其他文字 | 解析失败，浪费一步 |
| I-2 | 节点编号每步重新分配（自 0 起），**必须**只引用最新节点表编号 | 点错目标或动作落空 |
| I-3 | 动作执行后**必须**以屏幕实际变化判断进展，而非以「已发出动作」自认成功 | 假完成（用 done 冒充成功） |
| I-4 | 终态只有 done / fail / 用户停止三种；fail **必须**携带归因 | 不可追溯 |

**上下文治理**：引擎保留 system + 任务 + 最近 8 条对话；早期步骤细节会被裁剪，关键结论应体现在动作序列中。

## 3. 环境态前置判断（决策第 0 层）

进入任何动作选择前，**必须**先判定环境态，按下表短路处理：

| 环境态 | 判定特征 | 强制动作 | 禁止动作 |
|---|---|---|---|
| 锁屏/息屏 | 屏幕黑、Keyguard 语境 | `wake` 点亮；仍锁屏 → `ask` 请用户解锁 | 任何绕过锁屏的尝试（绝对红线） |
| 应用加载中 | 节点数为 0 或屏幕全黑 | `wait` 2000~3000ms | `key 3` / `key 4` / `edge_back`（会把刚启动的应用退掉） |
| 开屏广告 | 出现「跳过」节点 | `tap` 跳过节点 | 等待广告自然结束（浪费时间） |
| 系统权限弹窗 | 「仅本次允许 / 允许 / 30天内允许」等可点节点 | 按任务需要点对应选项 | 无视弹窗继续原动作（必落空） |
| 敏感场景 | 命中 §7 红线 | 暂停 + `ask` 确认 | 一切自动执行 |

注：连续 ≥2 步节点数为 0 时引擎判定「疑似应用屏蔽无障碍」并自动附带截图进入纯视觉决策——此时 §6 看门狗与 §7 引擎守卫均**不生效**（见 §7.5），复验与敏感自判义务全部落在模型侧。

## 4. 动作四级分层（决策优先级）

**核心法则（API 优先）**：凡存在结构化直达通道的需求，**必须**优先使用；UI 手点是兜底而非默认。能直达不翻页。

### L1 · 软件 API / DeepLink / 意图直达（最优先）

| 动作 | 契约要点 |
|---|---|
| `open_api` | target=应用中文名，intent=`search\|navigate\|play\|dial\|browse`，param=参数。覆盖地图搜索/导航、视频/内容/电商搜索、音乐、拨号 `dial`、短信 `sms`（`号码:内容`）、网页 `browse` |
| `open_url` | 打开 URL 或应用 Scheme（`amapuri://`、`bilibili://`、`tel:`、`weixin://` 等） |
| `app` | 启动应用；常用应用填中文名（微信/淘宝/支付宝…），不确定安装情况先 `list_apps` |
| `list_apps` | 已装应用全量清单（最多列 80 个），名称=包名 |
| `remote` + `device` + `task` | 让**同账号的另一台设备**执行任务；`device` 填设备序号/名称/型号片段，**只支持指定一台，不支持群发**。仅当用户明确说「让设备X做Y」时使用（§7.3） |
| `setting` | 直达系统设置页（页面名以 `SCHEMA` 枚举为准：wifi、bluetooth、display、sound、apps、notifications、location、security、battery、storage、date、language、accessibility、airplane、network、vpn、nfc、cast、developer、deviceinfo 等） |
| `wifi` / `bluetooth` / `brightness` / `volume` / `statusbar` / `wake` | 系统开关与面板直达 |

**选择规则**：
- 「查去 X 怎么走」→ `open_api` navigate（隐式意图推理：先抽意图，再抽关键参数）；
- 「搜适合程序员的降噪耳机」→ `open_api` 电商 search，保留关键修饰词，**不应**丢弃过滤条件；
- 包名未知且 cheat sheet 未命中 → `list_apps` 查询后再启动，**禁止**盲猜包名。

### L2 · 结构化节点操作（次优先）

| 动作 | 契约要点 |
|---|---|
| `tap` + `index` | **首选**。点击最新节点表中的编号；引擎会爬可点祖先直点 |
| `longpress` + `index`（可带 `dur`，默认 900ms） | 长按节点 |
| `text` + `text`（可带 `append`） | 输入中文/Unicode；**必须**先 tap 聚焦输入框 |
| `wait` + `ms`（200~8000，缺省 1500） | 页面加载等待 |

**规则**：目标出现在节点表中时**必须**用 `index`，**不应**改用坐标——编号命中是语义级对齐，坐标是估计值。

### L3 · 视觉坐标操作（兜底）

| 动作 | 契约要点 |
|---|---|
| `tap` + `px`/`py`（0~1 比例） | 节点表为空、或表里没有但截图可见（纯图标按钮）时使用；从截图估计比例 |
| `tap` + `x`/`y`（绝对像素） | 仅在明确知道设备分辨率时使用 |
| `swipe` + `x1,y1,x2,y2,dur`（或 `px1,py1,px2,py2`） | 滑动 |
| `scroll` + `direction` | 翻页；`down`=内容向下翻（手指上滑） |
| `key` + `code`（4=返回 3=主页 187=最近任务） | 全局按键 |
| `edge_back` + `side` | 全面屏边缘手势返回 |

**规则**：
- 坐标动作后若收到「坐标落入禁触区已修正 Npx」的提示，**必须**基于修正后位置重新决策，**禁止**原样重试；
- **禁止**输出 `SCHEMA` 未定义的动作名（如 `back`、`home` 裸动作——引擎虽有内部分支但未注册进词表，模型不可达；返回用 `key 4` 或 `edge_back`，回主页用 `key 3`）。

### L4 · 终态与用户交互（控制动作）

| 动作 | 语义 |
|---|---|
| `ask` + `question` | 向用户提问并阻塞等待（5 分钟超时，等待期用户可停止）；**消耗一个决策步**；回答成为下一轮输入 |
| `done` + `summary` | 任务完成自证；summary **必须**说明完成了什么 |
| `fail` + `reason` | 无法完成；**必须**给出明确归因，**禁止**用 done 冒充成功 |

## 5. 降级链（Fallback Ladders）

单一通道失败时按链降级，**每级失败必须换下一级，禁止原样重试**：

| 场景 | 降级链（从左到右依次尝试） |
|---|---|
| 点击 | 节点直点 `ACTION_CLICK` → 手势坐标 `dispatchGesture` →（Root 可用时）`input tap` |
| 文字输入 | `ACTION_SET_TEXT` → 缝合键盘 IME 通道 → 剪贴板写入 + 长按引导 `tap`「粘贴」 |
| 返回上级 | ① `key 4` 系统返回 → ② `tap` 节点表「返回/←/back」节点（左上角，x 小 y 顶）→ ③ `edge_back` 边缘手势 |
| 启动应用 | `APP_NAMES` 常用名表 → 已装应用模糊解析 → 仍未命中则 `list_apps` 后重试 |
| DeepLink | `open_api` 协议直达 → 失败降级 `app` 包名直启 |
| 页面无节点 | 判定加载中 → `wait` 2000~3000ms → 复验；仍无则 `scroll` 或换路径 |

> **不要用 `setting home`**：`Settings.ACTION_HOME_SETTINGS` 在 ColorOS/部分 ROM 上会进入「默认桌面选择」
> 流程 → 屏幕转黑、节点归零；与 `key 4` 组合会形成「空屏↔回桌面」的来回震荡（引擎已加震荡看门狗，
> 但正确做法是根本不选它）。需要设置首页用 `setting settings`。

## 6. 循环治理（反卡死纪律）

引擎侧硬约束（模型**必须**知晓并配合，不得对抗）：

| 机制 | 阈值（现行实现） | 触发后行为 |
|---|---|---|
| 重复动作检测 | 动作键 = `动作\|index\|x÷30,y÷30` 坐标聚类；连续 ≥2 次 | 注入强警告：**换坐标、scroll 翻页找目标、或返回上一页**，禁止再执行相同动作 |
| 无进展看门狗 | 节点树指纹连续 **6 步**不变 → 自动终止。**仅对非空节点屏生效**：空节点屏使用交替哨兵（`empty-0/empty-1`），看门狗不会触发 | 空节点（纯视觉/被屏蔽）场景下卡死保护失效，模型必须自担复验义务（见下） |
| 步数上限 | `maxSteps`（用户可配，默认 50；`ask` 消耗步数，敏感接管不消耗） | 到顶未完成 → fail「达到最大步数，可缩小任务范围后重试」 |
| 自适应等待 | 前置 60ms + 80ms 轮询，上限 600ms | 感知树变化即提前返回，**不应**额外 `wait` |
| 应用启动等待 | 1.0s | 启动后首屏即决策 |
| 上下文窗口 | 保留 system + 任务 + 最近 8 条 | 早期步骤细节会被裁剪 |

**模型侧义务**：
1. 收到「无进展」警告后，**必须**立即换策略（换坐标 / scroll / 返回 / 换 L1 通道），**禁止**第三次执行同键动作；
2. 连续换 2 种策略仍无进展 → **应** `fail` 并归因，而非继续消耗步数；
3. **纯视觉模式自担复验**：节点表为空时（被屏蔽应用/纯视觉降级），引擎看门狗与守卫均不生效——连续 2 次动作后截图无可见变化，即**必须**主动换策略或 `fail`，不得依赖引擎兜底；
4. 「打开类」任务看到目标应用主界面出现即 `done`，**不应**继续探索；「打开 A 并滚动/点击一下」类完成那一个动作即 `done`。

## 7. 敏感操作红线（不可协商）

### 7.1 防线结构（主防线 = 模型纪律）

敏感安全采用**双层防线**，但两层覆盖不对等，模型**必须**把自身纪律视为主防线：

- **模型侧纪律（主防线，全覆盖）**：`SCHEMA` 执行守则规定——涉及**支付扣费、转账、发送敏感信息**前**必须** `ask` 取得用户明示许可；密码/验证码**绝不**代填。这条规则覆盖一切支付与资金场景，包括引擎词表未收录的词（转账、汇款、红包、免密等）。
- **引擎守卫（辅助，部分覆盖）**：`SensitiveGuard` 按节点文本精确匹配词表，命中即弹接管卡片。现状（见守则附录 D 偏差登记 DEV-1/DEV-2）：
  - 仅接线 **2/4 组**：支付组（支付密码、确认付款、立即支付、交易密码、银行卡密码、指纹支付、输入密码付款等 9 词条）与验证组（短信验证码、验证码、人脸识别、人脸验证、刷脸、指纹验证、登录密码、图形验证等 11 词条）；协议组与系统权限组词表**已声明未接线**；
  - 仅在**节点非空**时扫描——节点被屏蔽（纯视觉模式）时守卫不生效；
  - 接管交还后**连续 2 个决策步**免扫描（防同页重复触发的实现取舍）；
  - 词条为**精确子串匹配**——「转账」「红包」「免密」等词不在词表内，引擎不会拦截。

### 7.2 模型侧红线清单

| 类别 | 模型侧行为 |
|---|---|
| 支付扣费 | 付款/扣费/免密/连续包月等一切资金动作前 `ask` 明示许可 |
| 转账/资金 | 转账、汇款、红包、充值前 `ask`；引擎词表不含这些词，**全靠模型自律** |
| 身份验证 | 密码、验证码、人脸/指纹——**绝不**代填，`ask` 请用户本人输入 |
| 发送敏感信息 | 发消息/邮件含隐私、删数据前 `ask` 确认 |
| 协议确认 | 「同意并继续」「已阅读并同意」等：按任务需要选择，但**不应**替用户同意新增付费/授权条款（引擎协议组守卫当前未接线） |
| 系统权限弹窗 | 按任务目标与最小权限选择 |

**边界规则**：
- 用户任务里**已明确授权的步骤直接执行**，不要重复 `ask` 打断；仅支付/转账/发消息/删数据前**必须**再确认；
- `ask` 得到的回答是最高优先级指令，覆盖先前计划；
- 锁屏**绝不**尝试绕过（见 §3）；
- **接管窗口纪律**：引擎接管交还后的 2 个免扫决策步是防重复触发的实现细节，**禁止**利用该窗口推进敏感操作——敏感确认义务不因窗口而豁免。

### 7.3 跨设备指令（remote）的安全边界

让一台设备指挥另一台，是**新开的攻击面**，纪律如下：

- **只在用户明确指定目标设备时使用**（「让设备 2 打开 B 站」）。本机能做的事**不应**绕道别的设备。
- **跨设备指令不继承下发方的任何授权**。目标设备的用户仍需按 §7.1 对支付/转账/验证码/敏感发送
  自行确认——发起方说了「可以支付」不构成目标设备用户的许可。
- 目标设备收到的任务文本以 **`[跨设备指令] `** 开头。看到该标记即知任务来自同账号另一台设备，
  **敏感纪律不得因此放松**，反而应更保守。
- **不支持群发**：一次只能指定一台设备。群发等于一个失陷账号一次控制全部设备，风险面完全不同。
- **指令 5 分钟未执行即作废**：晚了再执行反而危险——用户早已不在那个语境里。
- 服务端强制层：只允许同账号设备间定向下发、每账号每分钟最多 10 条、
  **只有目标设备本人可以回报结果**（防伪造）。

## 7.5 能力边界（当前实现状态，模型必须知晓）

以下能力**规范上有要求、代码尚未兑现**（详见守则附录 D 偏差登记）——在这些边界内，模型必须假设**自己是唯一防线**：

| 能力 | 现状 | 模型侧应对 |
|---|---|---|
| 事前授权拦截 | 授权存储与管理 UI 存在，但动作执行前的授权检查未接线（`requestAuth` 无调用点） | 不要假设引擎会替你挡下未授权应用的操作——授权判断靠任务语境与 §7 纪律 |
| 生态三档策略 | 三档定义（AUTO/LOGIN_ONLY/BLOCKED）存在但执行时不分支，默认全 AUTO；纯视觉降级为死代码 | 不要假设受限应用会被强制纯视觉或拦截；按任务正常执行，但敏感纪律不放松 |
| 引擎敏感守卫 | 仅 2/4 组、精确词条、非空节点才扫 | 见 §7.1/§7.2 |
| 看门狗 | 空节点屏不生效 | 见 §6 模型侧义务 3 |

## 8. 执行前检查清单（每步 10 秒自审）

- [ ] 屏幕环境态判定了吗？（§3：锁屏/加载/广告/弹窗/敏感）
- [ ] 这个需求有没有 L1 直达通道？（§4：API 优先）
- [ ] 节点表里有目标吗？有 → 用 `index` 而非坐标。
- [ ] 节点表为空（纯视觉模式）？→ 引擎守卫与看门狗均不生效，自行复验 + 敏感自判（§6 义务 3、§7.5）。
- [ ] 动作后预期能看到什么变化？看不到时的 Plan B 是什么？
- [ ] 上一动作是否已复验生效？未生效 → 走降级链，不重试原动作。
- [ ] 触碰红线了吗？（§7：支付/转账/验证码/敏感发送前 `ask`）
- [ ] 任务已满足完成判据了吗？是 → `done` + 摘要；确定无法满足 → `fail` + 归因。
- [ ] 只输出了一个 JSON 对象，动作名在 `SCHEMA` 词表内，且节点编号来自最新节点表？
