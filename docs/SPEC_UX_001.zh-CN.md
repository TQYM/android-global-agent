# SPEC-UX-001：零门槛守则（Zero-Friction Onboarding Spec）

> 状态：**生效中**（2026-09-14 起）· 归属项目：`agent-lite` · 依据：`PROJECT_OVERVIEW.zh-CN.md` §16
> 门禁：`python3 tests/spec_ux_001_guard.py`（已并入 `make check`）

## 0. 这份规范解决什么

项目此前降低了**操作**门槛（自然语言、语音、无障碍自动执行），但没有降低**技术**门槛：
新用户仍可能被要求理解 API Key、Base URL、模型名、RAM 子账号、资源包匹配与无障碍设置。
那等于把门槛从「写代码」换成「懂云服务」。

本规范把「极大降低技术门槛」变成**可验收**的条款，每条都绑定一个可自动检查的断言或一个
明确的真机回归动作。

## 1. 条款（可验收）

| ID | 条款 | 验收方式 | 门禁断言 |
|---|---|---|---|
| UX-1 | **五分钟首成功**：全新用户不查文档、不填 Base URL/API Key/模型名，五分钟内完成一项安全任务（打开应用 / 打开设置） | 真机回归：清数据 → 登录 → 说一句话 → 完成 | `UX-1` |
| UX-2 | **首屏零技术词**：首屏与首轮引导不得出现 API、Base URL、endpoint、模型名、RAM、token | 静态扫描 `activity_main.xml` 可见文案 | `UX-2` |
| UX-3 | **无效请求前置拦截**：无可用凭据时禁止向模型发请求，改为一张可操作的解决卡 | 运行入口先判凭据再启动 | `UX-3` |
| UX-4 | **每个失败可恢复**：失败必须含人话原因 + 下一步动作 + 可重试入口；禁止把 Java/HTTP/云厂商原文直接示人 | 失败归因统一经 `UiText.uiReason` 加工 | `UX-4` |
| UX-5 | **权限渐进申请**：只在功能需要时申请；一次只解释一类；拒绝后有降级路径 | 权限申请点不得集中在启动期 | `UX-5` |
| UX-6 | **状态可解释**：自动动作要显示「正在做什么 / 操作哪个应用 / 如何停止」；敏感操作暂停等用户（**协议类例外见 §1.1**） | 状态卡片与胶囊文案来源唯一 | `UX-6` |
| UX-7 | **结果可证明**：`done` 必须有该动作的最小验收证据；无法证明时只能继续复验或 `fail` | 引擎内存在完成复验分支 | `UX-7` |
| UX-8 | **设置可恢复**：配置在冷启动、进程死亡、升级后保持；危险设置可撤销；清理必须版本化迁移 | 迁移代码存在且版本化 | `UX-8` |
| UX-9 | **受限设备可用**：无截图 / 无障碍被屏蔽 / 网络不稳时给出降级路径或清晰原因，不得无限重试 | 感知降级链与重试上限存在 | `UX-9` |
| UX-10 | **副本与模型同源**：动作词表、执行分支、友好文案、测试有单一事实源，并带 `SCHEMA_VERSION` | 真身与 unified 副本一致 + 版本常量 | `UX-10` |

### 1.1 协议类弹窗的例外（2026-09-18 修订）

原条款要求「条款/隐私弹窗**只检测不代点**」（引擎不替用户同意协议）。2026-09-18 用户明确要求
「取消服务条款限制，改成完全无限制」，故修订为：**引擎可以代点协议类弹窗，但必须同时满足**——

1. 由 `Prefs.autoAcceptTerms()` 控制（**默认开**）；
2. 关闭开关时，代点方法**立即短路返回**，退回「暂停并把控制权交还用户」。

> ⚠️ **风险已知并接受**：代点「同意并继续」等于**代替用户作出法律授权**，且通常**不可逆**
> （用户接受了未曾阅读的条款）。建议只在自己信任的 App 上使用；随时可用
> `Prefs.setAutoAcceptTerms(false)` 关回安全默认。
>
> 门禁断言相应从「绝不代点」改为「**代点必须可关闭**」——防止将来被硬编码成无法退回的行为。
> 其余敏感红线（支付 / 转账 / 验证码 / 删除数据）**不在本例外内**，仍必须暂停等用户。

## 2. 三条凭据路径（UX-3 的落地形态）

用户能开始的合法路径**只有**这三条，界面必须让第一条成为默认：

1. **登录账号**（推荐）：用账号额度，用户不需要知道任何云服务概念；
2. **自带 Key**（高级）：放在「设置 → 高级」里，录入前解释用途、风险与撤销方式；
3. 未登录但已填 Key：可用（离线/自备场景），同样在高级页。

无凭据时：**不发请求**，弹一张解决卡（唯一主按钮 = 登录 / 领取额度，次按钮 = 打开设置）。

## 3. 与既有规范的关系

- 终态与归因文案：`docs/INTERACTION_LOGIC_SPEC.zh-CN.md` §9（T-4 / O-3）——本规范不重复定义，
  只要求「失败可恢复」这一层由守卫与卡片保证。
- 动作契约与 `SCHEMA_VERSION`：见 §16.5「推荐动作契约」，本规范只做门禁（UX-10）。
- 敏感红线（支付/发送/删除/授权）：`skills/software-interaction-logic`——引擎不可绕过，
  不得由模型自行判断能否越过。

## 4. 维护

新增条款必须同时提供「验收方式 + 门禁断言」；无法自动化的条款写进真机回归清单
（`make check` 输出会提示未覆盖项）。条款变更需同步 `PROJECT_OVERVIEW.zh-CN.md` §16 与
`tests/spec_ux_001_guard.py`。
