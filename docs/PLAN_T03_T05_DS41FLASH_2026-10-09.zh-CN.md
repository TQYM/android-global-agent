## 2. T05a · 任务代际防护（状态：**已实施** 2026-10-09）

**目标**：旧任务的延迟回调不得撤掉/改写新任务的界面与服务状态。

**现状证据**（2026-10-09 亲自核验，行号为当前工作树）：

- [OverlayController.java:162–164](<../agent-lite/src/com/dsh/agentlite/OverlayController.java#L162-L164>)：`taskEnded(true)` 后 4 秒 `postDelayed` **无条件** `removeView(capsule)`——而同方法 169–171 的 15 秒卡片回收分支**有** `if (!taskActive)` 守卫（注释还写明「taskActive 判断避免误撤新任务的卡片」）。4 秒分支漏了同样的守卫：任务 A 完成保留结果，4 秒内用户启动任务 B，A 的定时器会把 B 的胶囊撤掉。
- [AgentEngine.java:277–279](<../agent-lite/src/com/dsh/agentlite/AgentEngine.java#L277-L279>)：`start` 的 finally 里 `postDelayed(… KeepAliveService.updateState(app, false), resultShown ? 4000 : 1000)` 未绑定任务代际——旧任务收尾延迟回调可能把新任务的前台服务状态置 false。

**修改步骤**：

1. `OverlayController.taskEnded` 162–164 补守卫：`ui.postDelayed(() -> { if (!taskActive) { removeView(capsule); capsule = null; } }, 4000);`
2. `AgentEngine` 加代际序号：`private static final AtomicLong RUN_SEQ = new AtomicLong();`（`java.util.concurrent.atomic`）；`start` 线程体开头 `final long mySeq = RUN_SEQ.incrementAndGet();`；finally 的延迟回调改为 `if (mySeq == RUN_SEQ.get()) KeepAliveService.updateState(app, false);`
3. 测试（先写）：
   - 新静态门禁 `tests/generation_guard.py`：① 提取 `taskEnded` 方法体，每个 `postDelayed` 之后的 lambda 必须含 `taskActive` 判断；② `AgentEngine.java` 中 `postDelayed` + `updateState` 组合必须伴随 `mySeq ==` 比较。当前代码上跑必须 FAIL。
   - 真机（卡收尾跑一次）：任务 A（mock done）→ 3 秒内启动任务 B → `adb shell dumpsys window` 断言 B 的胶囊窗口仍存在、`dumpsys activity services` 前台服务未停。

**禁止**：不动 15 秒分支语义；不改 `taskEnded` 其它退场行为。

## 4. T04a · done 证据分级与入库门槛（状态：**已实施** 2026-10-09）

**目标**：消除「二次 done 无证据放行」与「无证据成功进 FlowMemory」。

**现状证据**：

- [AgentEngine.java:920–932](<../agent-lite/src/com/dsh/agentlite/AgentEngine.java#L920-L932>)：第一次无证据 done 追问一次（923），**第二次无条件接受**（`doneVerifyAsked=true` 使条件短路）；
- [AgentEngine.java:938–948](<../agent-lite/src/com/dsh/agentlite/AgentEngine.java#L938-L948>)：`recordable && !recordedSteps.isEmpty()` 即写操作记忆库；
- 全景 §18.3-2 定性为 P0：屏幕变化只证明「可能发生动作」，不证明目标达成。

**修改步骤**：

1. 新增纯静态判定（无 android 依赖，便于桌面 JVM 直测）：`static int judgeDone(boolean sawFgChange, String expectPkg, String activePkg)`，返回 `PROVEN / WEAK / UNPROVEN` 三常量：`expectPkg` 非空且 `activePkg` 等于它 → PROVEN；仅 `sawFgChange` → WEAK；否则 UNPROVEN。
2. done 分支接入：PROVEN → 现行完成路径（入库维持现状）；WEAK → 完成展示维持，**本刀不改入库**（标注 T04b 后续）；UNPROVEN → 终态改为「结果不确定」：`history("不确定", …)` 文案如实（例：未观察到完成证据，结果待人工确认）、`recordable = false`（不入库）、完成卡文案降级但不出现在「完成」语义位。
3. 测试（先写，抽取法照 [credential_route_guard.py](<../tests/credential_route_guard.py>) 的 harness 模式）：
   - 桌面 JVM：`judgeDone` 真值表全组合 + UNPROVEN 时 `FlowMemory.commit` 不被调用的守卫断言；
   - mock 真机：[mock_llm_server.py](<../tests/mock_llm_server.py>) 场景一——连续两次回复 `{"action":"done"}` 无任何动作 → 断言终态「不确定」且记忆库文件无新记录（当前代码 FAIL：会记「完成」并可能入库）；场景二——`app 计算器` 后前台确已切换再 done → 断言 PROVEN 且入库。
4. 真机回归收尾（三卡全完后统一跑，见 §5）。

**禁止**：不删 doneVerifyAsked 追问逻辑；不动 ask/fail 分支；「不确定」终态文案不得出现「完成」字样；WEAK 入库行为本刀不动。
