## 0. 这份方案解决什么（TL;DR）

**问题**：现在的链路能听懂「打开微信」，但听不懂「老样子来一杯」「再把它关了」「帮我搞定明天的会」。
用户说的是**人话**，引擎要的是**可执行的结构**——中间那层转译目前只有 3 行纯文本的「规划简报」，
既不是结构化流程，也不澄清、不复用、不消解指代。

**方案**：在用户输入与引擎主循环之间，新增一层**语义转译层（Semantic Translation Layer, STL）**，
把模糊自然语言转译为一份**结构化流程 `FlowSpec`**，再编译成现有的首条 user message 注入。

**三条硬约束（本方案的全部风险控制都在这里）**：

| # | 约束 | 理由 |
|---|---|---|
| C-1 | **不新增模型往返**：把现有 `planTask()` 升级为转译调用，而不是在它之外再加一次请求 | 现状每次任务已有 1 次规划往返；再加一次 = 延迟与 token 双涨，且单模型模式下走的是**主模型**（贵） |
| C-2 | **不动引擎主循环、动作词表、复验、看门狗** | `SCHEMA`/`ActionSchema`/循环不变量是项目最稳定的部分，动它要重跑全部门禁与真机回归 |
| C-3 | **任何失败都回退到今天的路径**（转译层是纯增益，不是必经关卡） | 与 `planTask` 现有的失败容错姿态一致（`AgentEngine.java:1233-1236`） |

## 1. 现状与缺口

### 1.1 现有链路（代码事实）

```text
用户输入（6 条入口，见 §1.4）
      │
      ▼
AgentEngine.runLoop(task)                      AgentEngine.java:396
      │  ├─ system 提示词 = prefs.systemPrompt()
      │  │                  + MemoryStore.promptBlock()   记忆，最近 15 条/1000 字
      │  │                  + RemoteCommand.deviceBlock() 同账号设备列表
      │  │                  + SCHEMA                      动作词表+守则
      │  │                                                 AgentEngine.java:410-414
      │  ├─ planTask(prefs, task)  ← 唯一的「语义理解前置」
      │  │     轻量模型产出 3 行纯文本：意图/直达建议、推荐应用、步骤提炼
      │  │                                                 AgentEngine.java:1211-1237
      │  ├─ matchInstalled(task)   已装应用模糊解析 → 真实包名
      │  └─ 首条 user message = "任务：" + task + 已装应用 + 【规划简报】
      │                                                     AgentEngine.java:417-423
      ▼
主循环 for step in 1..maxSteps                 AgentEngine.java:442
      │  每步：trimHistory(keep=8) → 感知 → 1 个 JSON 动作 → exec() → 复验 → 看门狗
      ▼
终态 done / fail / 用户停止
```

### 1.2 `planTask` 的四条硬伤

| # | 硬伤 | 证据 | 后果 |
|---|---|---|---|
| G-1 | **非结构化**：输出 3 行中文散文，字段靠模型自觉 | `AgentEngine.java:1223-1227` | 无法校验、无法复用、无法统计；模型可以自由跑偏而引擎看不见 |
| G-2 | **一次性**：结果只拼进首条 message，用完即弃 | `AgentEngine.java:422` | 同类任务第二次仍要重新规划；用户的偏好与上次的选择全部丢失 |
| G-3 | **不澄清**：任务有歧义时只能由主循环用 `ask` 救场 | 守则 §4 L4（`ask` 消耗一个决策步） | 澄清发生在**引擎步内**，冷却期已过、上下文已裁剪（`HISTORY_KEEP=8`，`AgentEngine.java:114`），问出来的问题往往已经问不准 |
| G-4 | **不消解指代**：「它」「那个」「老样子」没有任何实体账本 | 全仓无实体表；`MemoryStore` 只存用户显式说的「记一下…」 | 指代只能靠 system 里那点记忆硬猜，猜错就是执行错 |

### 1.3 五类「模糊」在本项目的具体形态

| 类型 | 真实说法（示例） | 今天会发生什么 |
|---|---|---|
| **F-1 口语化与省略** | 「点个奶茶」「打车回家」 | 缺品类/地址参数，模型自行脑补；错也错得静默 |
| **F-2 指代与上下文继承** | 「再把它关了」「换成第二家」 | 「它」无从解析；上一轮的实体（哪家店、哪个应用）完全丢失 |
| **F-3 歧义与信息不足** | 「订明天的会」 | 订哪个应用（飞书/腾讯会议）？几点？多久？—— 靠 `ask` 事后补救 |
| **F-4 流程复用** | 连续三天说「点昨天那杯」 | 每次都从零规划，token 照付，路径还可能漂移 |
| **F-5 语音 ASR 噪音** | 「打开美团搜奶查」（奶茶） | 错字直接进任务文本，模型靠猜；链路已解耦 ASR 端点（手册 §16.14）但没有纠错层 |

### 1.4 输入入口清单（实测：共 6 条，无磁贴/Shortcut）

STL 必须知道**任务从哪来**，因为不同来源的澄清策略不同（§8 D-7）。经逐条核实：

| # | 入口 | 代码位置 | 是否进 STL | 备注 |
|---|---|---|---|---|
| E-1 | 主界面文本框 | `MainActivity.java:416` | ✅ 是 | 主入口 |
| E-2 | 语音（录音→ASR→执行） | `MainActivity.java:496-511` | ✅ 是 | **F-5 的主战场** |
| E-3 | 系统助手 `AssistActivity` | `AssistActivity.java:126-134` | ✅ 是 | 走**进程内**通道传任务（`setPendingTask`），因 Intent extra 会暴露给任意应用（安全审查 P0-1） |
| E-4 | 胶囊面板「重试一次」 | `OverlayController.java:359-361` | ⚠️ **否** | 复用 `engine.lastTask()` 原样重试，**不应**重新转译（用户要的是"再来一次"，不是"重新理解"） |
| E-5 | 跨设备指令轮询 | `RemoteCommand.java:274`（`REMOTE_PREFIX = "[跨设备指令] "`，`:58`） | ✅ 是（**只读不澄清**） | 见 D-7：来自远端，不弹本机澄清卡片 |
| E-6 | 执行中补充指令 | `AgentEngine.java:232-236` 入队 → `:483-493` 注入 | ❌ **否** | 补充指令在**循环内**注入（"优先级高于原任务"），要求低延迟；走 STL 会引入一次模型往返，把在线修正变成离线批处理 |

> **E-4 / E-6 刻意不进 STL**：转译层是**任务级**的，不是消息级的。把它塞进重试与在线修正路径，
> 只会让本该"立刻"的动作多等一次模型往返。这张表也是 P0 落地时的**接线范围说明**——
> 只在 E-1/E-2/E-3/E-5 的 `runLoop` 入口前置 STL。

## 2. 目标与非目标

### 2.1 目标

| ID | 目标 | 可验证判据 |
|---|---|---|
| O-1 | 模糊输入产出**结构化流程** | 每次转译产出合法 `FlowSpec`（§4.1）；非法即丢弃并回退 |
| O-2 | 指代消解**不依赖循环内历史** | 转译在任务开始前完成；实体来自 `ContextLedger`（§4.3），与 `HISTORY_KEEP` 无关 |
| O-3 | 歧义**前置澄清**，且用户**只需点选** | 澄清发生在引擎启动前，选项是按钮（§5.3）；与零门槛守则 UX-2 一致（不得出现技术词） |
| O-4 | 同类流程**可复用** | 相同指纹命中 `FlowStore` 后**跳过模型调用**（§5.4），可量化命中率 |
| O-5 | 转译层**零新增往返、零新增配置项** | 复用 `Prefs.plannerModel()` 通道（`Prefs.java:173-177`）；不新增设置项 |
| O-6 | 失败**绝不阻塞**主流程 | 超时 3s / 异常 / JSON 非法 → 原路径执行（§8） |

### 2.2 非目标（明确不做）

- ❌ **不做端侧小模型**：不引入 ONNX/TFLite 推理，转译仍走已有 LLM 通道（端侧算力与包体都不划算）。
- ⚠️ **「不做全自动流程学习」已被用户要求改写（2026-09-19）**：原文是不从历史动作序列里挖流程。
  用户明确要求「每一步成功执行的操作进记忆库，之后直接复现就能完成操作」，故改为：
  **只收「本次任务在 `done` 终态时」的那条动作序列**（已知它成功、且正是用户刚提出的那件事），
  而**仍然不做**跨任务的历史行为挖掘——那才是原禁令真正要防的隐私代价。
  边界不变的部分（敏感流程不入库 / 凭据不入库 / 不上云 / 本地可删）见 §9.3，
  并已由 `tests/flow_memory_guard.py` 逐条看守。
- ❌ **不替代 `ask`**：STL 只做**执行前**澄清；执行中遇到敏感确认（守则 §7）仍由主循环 `ask` 负责，两套机制并存。
- ❌ **不做跨设备澄清**：`[跨设备指令]` 一律不弹澄清卡片（§8 D-7），原因见守则 §7.3。
- ❌ **不接管执行中的补充指令**：补充走循环内注入（`AgentEngine.java:483-493`），要求低延迟，
  不进 STL（§1.4 E-6）。
- ❌ **不改动作词表**：本次不新增 `ActionSchema` 条目，`SCHEMA_VERSION` 不变（若后续要加 `clarify` 动作，须走 UX-10 的三处同步流程）。

## 3. 总体架构

```text
                        ┌─────────────────────────── STL：语义转译层 ───────────────────────────┐
用户输入 raw            │                                                                        │
  │                     │  ① N 归一化         ② U 理解              ③ C 澄清门控                │
  ├─ 文本框  (E-1)      │  Normalizer   ──▶   Resolver      ──▶    ClarifyGate  ──┐              │
  ├─ 语音    (E-2)      │  · 填充词剥离        · 意图识别             · 置信度判定  │              │
  ├─ 系统助手(E-3)      │  · 同音错字表        · 槽位抽取             · 关键性判定  │  需要澄清     │
  └─ 跨设备  (E-5)      │  · 数字/单位规整     · 指代消解 ◀─┐         · 选项生成    ▼              │
                        │                      · 置信度      │                      澄清卡片      │
                        │                                   │                    （用户点选）    │
                        │  ④ T 转译                                          │                  │
                        │  Translator                                        │                  │
                        │  · 指纹命中 FlowStore ──▶ 变参重放（跳过模型）      │                  │
                        │  · 未命中 → 一次 LLM 调用（复用 plannerModel）──────┘                  │
                        │  · JSON 校验 + 风险标注                                                │
                        └────────────────────────────┬───────────────────────────────────────────┘
                                                     │ FlowSpec
                                                     ▼
                                       ⑤ E 编译 → 首条 user message
                                          （替换今天的【规划简报】位置）
                                                     ▼
                                       现有引擎主循环（一行不改）
```

> **旁路入口**：E-4（胶囊重试）与 E-6（执行中补充）**不进 STL**——前者复用 `lastTask()` 原样重试，
> 后者在循环内低延迟注入。理由与代码位置见 §1.4。

**分层职责与不变量**

| 层 | 职责 | 不做什么 |
|---|---|---|
| ① N 归一化 | 只做**确定性**清洗（规则表），不做语义改写 | 不猜用户想干什么 |
| ② U 理解 | 产出 `IntentFrame`：意图 + 槽位 + 置信度 + 歧义清单 | 不产出动作，不碰 `SCHEMA` |
| ③ C 澄清 | 只在**歧义影响执行**时打断，且必须给可点选项 | 不索取密码/验证码（守则 §7.1） |
| ④ T 转译 | 产出可校验的 `FlowSpec`；维护流程库 | 不执行、不预演动作 |
| ⑤ E 编译 | 把 `FlowSpec` 渲染成提示词文本 | **不新增动作**，不改循环 |

**关键设计取舍**：STL 的产物是**提示词**，不是动作序列。引擎仍然一步一个 JSON 动作地走
（不变量 I-1）。这样做的好处是：STL 出错最多让模型"理解得差一点"，**不会让引擎执行错动作**——
风险被限制在理解层，执行层的安全保证（复验、看门狗、`SCHEMA` 校验、敏感守卫）原样有效。

## 4. 数据结构

### 4.1 `FlowSpec`（转译产物，核心）

```json
{
  "v": 1,
  "intent": "order_food",
  "goal": "在美团给用户点一杯奶茶（少冰三分糖），送到公司",
  "target_app": { "name": "美团", "pkg": "com.sankuai.meituan", "source": "installed" },
  "slots": {
    "品类": { "value": "奶茶", "source": "utterance",  "confidence": 0.95 },
    "甜度": { "value": "三分糖", "source": "memory",     "confidence": 0.90 },
    "地址": { "value": "公司",   "source": "ledger",     "confidence": 0.72 }
  },
  "steps": [
    { "n": 1, "do": "启动美团",              "channel": "app",           "expect": "美团首页",   "guard": "none" },
    { "n": 2, "do": "搜索「奶茶」",           "channel": "open_api:search","expect": "搜索结果",   "guard": "none" },
    { "n": 3, "do": "选销量最高的第一家",      "channel": "ui",            "expect": "店铺页",     "guard": "none" },
    { "n": 4, "do": "加入购物车并结算",        "channel": "ui",            "expect": "结算页",     "guard": "ask"  }
  ],
  "done_when": "结算页出现目标商品且金额与地址正确",
  "risk": "money",
  "must_ask_before": ["提交订单", "开通会员", "同意协议"],
  "carry_over": ["店铺", "商品", "地址"],
  "confidence": 0.86
}
```

字段契约：

| 字段 | 类型 | 约束 |
|---|---|---|
| `v` | int | 结构版本；**递增规则**：字段语义变化时 +1（与 `ActionSchema.SCHEMA_VERSION` 同思路，`ActionSchema.java:33`） |
| `intent` | string | 取自**受限意图表**（§5.4.1），未知意图只能是 `"general"` |
| `target_app.pkg` | string | **必须**来自 `matchInstalled()` 的真实匹配结果或 `APP_NAMES`；禁止模型自造包名（守则 §5「包名未知先 `list_apps`」） |
| `slots.*.source` | enum | `utterance` \| `memory` \| `ledger` \| `default`——**来源必须可追溯**，这是澄清与纠错的依据 |
| `steps[].channel` | enum | 只能是 L1 通道（`app`/`open_api:*`/`open_url`/`setting`）或 `ui`；用于统计「直达率」（守则 §4 API 优先） |
| `steps[].guard` | enum | `none` \| `ask`；`money/delete/send/personal_info` 风险的任务**必须**至少有一步 `ask` |
| `risk` | enum | `none` \| `personal_info` \| `send` \| `delete` \| `money`（与守则 §7.2 红线清单一一对应） |
| `must_ask_before` | string[] | 关键词列表，编译进提示词，与 `SensitiveGuard` 词表**互补**（守卫只覆盖 2/4 组，见守则 §7.1） |
| `carry_over` | string[] | 本次任务结束后要写进 `ContextLedger` 的实体名 |
| `confidence` | double | 0~1，模型自评；**低于阈值只影响是否澄清，不影响是否执行**（§5.3） |

### 4.2 `IntentFrame`（理解层中间产物）

```json
{
  "raw": "再把它关了",
  "normalized": "把它关了",
  "intent": "toggle_off",
  "slots": { "目标": { "value": "蓝牙", "source": "ledger", "confidence": 0.81 } },
  "ambiguities": [
    { "slot": "目标", "critical": true, "candidates": ["蓝牙", "WiFi"], "reason": "上一轮同时出现过两者" }
  ],
  "confidence": 0.81
}
```

`ambiguities[].critical` 决定要不要澄清：**关键槽位缺失/多义 = critical**；非关键修饰词（口味、排序方式）
不进澄清，直接取默认值并在结果卡片里标注（不打断用户）。

### 4.3 `ContextLedger`（实体账本，跨任务持久化）

解决 F-2，且**不依赖循环内历史**（O-2）。

```json
{
  "v": 1,
  "recent": [
    {
      "at": 1789000000000,
      "task": "打开美团搜奶茶",
      "intent": "search",
      "entities": { "app": "美团", "品类": "奶茶", "店铺": "喜茶" },
      "outcome": "done"
    }
  ]
}
```

| 规则 | 值 | 理由 |
|---|---|---|
| 保留轮数 | 最近 **5 轮** | 与 `HISTORY_KEEP=8`（对话条数）解耦；账本是**任务级**的，不是消息级的 |
| 存储 | `filesDir/ledger.json`（与 `memories.json` 同目录，`MemoryStore.java:29-31`） | 复用既有落盘惯例，不引入新存储 |
| 写入时机 | 终态为 `done` 时写；`fail` **不写** | 失败任务的实体不可信，写进去只会污染下一次消解 |
| 是否上云 | **否**（不接 `SyncClient`） | 实体账本含高频位置/消费信息，隐私代价高于同步收益；`MemoryStore` 上云是因为那是用户**显式**要求记住的 |
| 指代解析 | 「它/那个/这家/老样子」→ 按**最近优先 + 意图相容**取候选 | 例：「再把它关了」的意图是 `toggle_off` → 优先取上一轮出现过的开关类实体 |

### 4.4 `FlowRecord` 与指纹（流程库）

```json
{
  "fp": "a3f1c2…",
  "intent": "order_food",
  "skeleton": "点<品类>送到<地址>",
  "flow": { "…": "FlowSpec 去掉具体槽位值后的模板" },
  "hits": 7,
  "last_used": 1789000000000,
  "created": 1788000000000
}
```

**指纹算法**（必须在 `tests/` 里可复现，不能靠模型）：

```text
fp = sha1( intent + "|" + 归一化骨架 )
骨架 = 去填充词后的任务文本，把槽位值替换为 <槽位名> 占位符
例：「点个奶茶送到公司」→ "点<品类>送到<地址>" → fp=…
     「点杯咖啡送到公司」→ 同骨架 → 命中 → 只替换 品类=咖啡
```

| 规则 | 值 |
|---|---|
| 命中门槛 | `fp` 相同 **且** 命中记录 24h 内有成功记录 |
| 命中后 | **跳过 LLM 转译**（省一次往返），直接变参重放 |
| 写入门槛 | 终态 `done` **且** 用户未在本次任务中纠正过槽位 |
| 容量 | 最多 50 条，LRU 淘汰 |
| 敏感排除 | `risk != "none"` 的流程**不入库**（§9.3） |

#### 4.4.1 落地实现（2026-09-19）：`FlowPlan` + `FlowMemory`

草案里的 `FlowStore` 落地为两个类，判断与搬运分离（与 `FuzzyFlow` / `SemanticTranslator` 同一分层）：

| 类 | 层 | 职责 |
|---|---|---|
| `FlowPlan`（纯逻辑，零 android / org.json） | 判断 | 指纹、入库把关、锚点定位、新鲜度与退役、容量淘汰 |
| `FlowMemory`（android 侧） | 搬运 | 落盘 `filesDir/flowmem.json`、命中统计、UI 列表、骨架提示注入 |
| `AgentEngine` | 胶水 | 逐步采集成功动作、`done` 时入库、命中时直接复现 |

与草案的三处**有意偏差**（每处都有对应门禁看守，见 `tests/flow_memory_guard.py`）：

1. **指纹分两级**：`exactFp = sha1("exact"|归一化任务)` 与 `skeletonFp = sha1(intent|骨架)`。
   前者在**转译之前**即可判定，所以「同一句话再说一次」是**零模型往返**（连转译都省掉）；
   后者等转译结果，只用于给回退后的模型注入一行「上次同款」。草案只写了骨架级，
   单靠它达不到用户要的"直接复现"。
2. **可复现动作白名单**（`FlowPlan.REPLAYABLE`）：只有
   `app / tap / longpress / text / key / back / home / edge_back / swipe / scroll / wait / open_url`。
   `remote`（跨设备副作用）、`open_api`（支付/短信参数与当次语境绑定）、`list_apps`（信息动作）、
   `setting` 类系统开关一律不收——**出现其一即整条流程作废**，而不是跳过那一步：
   半条流程照做会在用户毫无察觉的情况下走错分支。
3. **锚点优先、比例为辅**：复现时先在当前屏幕按
   `resource-id → 文本相等 → 文本包含（两边都 ≥2 字）→ 类名唯一` 重新定位，
   定位不到才退到记录的比例坐标（`px/py ∈ [0,1]`，跨分辨率/跨设备可用），
   两者都没有就**放弃复现**而不是猜。这是"界面改版后仍能照做"与"死坐标回放"的分界。

> 复现全程复用既有 `AgentEngine.exec()`，因此手势降级、root 兜底、输入法借用、敏感场景守卫
> 与模型驱动时**完全一致**——记忆库不会变成第二条有自己缺陷的执行路径，也不是免检通道。

## 5. 机制详解

### 5.1 ① 归一化（F-1 / F-5）

**只做确定性变换**，一张规则表，纯函数、可单测（项目惯例：`UiText` 就是这样的纯函数类）：

| 规则 | 输入 → 输出 | 备注 |
|---|---|---|
| 填充词剥离 | 「帮我」「麻烦」「给我」「那个啥」→ 删 | **不得**删掉否定词（「别」「不要」）——删除表用白名单制 |
| 同音/形近纠错 | 「奶查」→「奶茶」、「美団」→「美团」 | 词表来自 `APP_NAMES` + 意图表关键词；**只纠高置信错字**，不确定不动 |
| 数字与量词规整 | 「十点半」「半小时后」「俩」→ 规范化表达 | 只规整形态，不做时间推算（推算是执行期的事，会过期） |
| 空白与标点 | 全角→半角、连续空白折叠 | — |
| 保留原文 | `IntentFrame.raw` 原样保留 | 结果卡片可回显「我听到的是：…」，用户可纠正 |

**ASR 噪音的三道处理**（F-5）：

1. **规则纠错**（上面第 2 条）——零成本、离线、可解释；
2. **模型纠错**——在转译的同一次调用里做（提示词明确要求"识别并纠正 ASR 错字"），**不额外发请求**（C-1）；
3. **关键槽位回读**——仅当纠正后的关键槽位 `confidence < 0.6` 时，在启动卡片上回显
   「我理解的是：在美团点奶茶（少冰三分糖）」并在 **2s 内可点「不对」纠正**；不打断执行。

> ⚠️ ASR 端点已解耦（手册 §16.14），本层**不依赖**具体 ASR 实现，只吃文本。

### 5.2 ② 理解与指代消解（F-2）

`Resolver` 的输入是归一化文本 + `ContextLedger` + `MemoryStore.promptBlock()`，产出 `IntentFrame`。
指代消解规则（**代码实现，不是提示词祈祷**）：

```text
代词命中表：它/他/她/这个/那个/这家/那家/老样子/还是那个/上次那个
      │
      ├─ 无候选 → ambiguity{critical=true} → 澄清
      ├─ 唯一候选 → 直接绑定，source=ledger，confidence=0.9
      └─ 多候选 → 按 (意图相容 > 时间最近) 排序：
                   Top1 与 Top2 分差 ≥ 0.3 → 绑定 Top1（source=ledger）
                   否则 → ambiguity{critical=true, candidates=[Top1,Top2]} → 澄清
```

「老样子」是特殊情况：它是**复合指代**，绑定上一轮 `done` 任务的**全部槽位**（这正是 `ContextLedger`
存 `entities` 而非只存最后一项的原因）。

### 5.3 ③ 澄清门控（F-3）

**澄清是成本，不是礼貌**。每次澄清要多一次用户交互、多一次模型调用、多 2~5 秒。
所以门控必须严格：

| 条件 | 行为 |
|---|---|
| `ambiguities` 为空 | 静默执行（绝大多数情况） |
| 有歧义但**均非 critical** | 取默认值执行，结果卡片标注「按 X 理解」 |
| 有 **1 个** critical 歧义，且候选 ≤ 3 | **弹澄清卡片**：一句话 + 最多 3 个按钮 + 一个「都不是，我自己说」 |
| 有 ≥2 个 critical 歧义 | 弹一张卡片**合并**问（不连续弹多张） |
| 已澄清过 1 轮仍有歧义 | **不再问**，取 Top1 执行，终态卡片标注「按 X 理解，可回复纠正」 |
| 来源是 `[跨设备指令]` | **不澄清**，直接 `fail` 带归因（§8 D-7） |

**澄清卡片的形态**（复用既有卡片通道）：

```text
┌────────────────────────────────────────────┐
│ 你指的是哪一个？                             │
│  「再把它关了」                              │
│  ┌────────┐ ┌────────┐ ┌──────────────┐   │
│  │ 蓝牙   │ │ WiFi   │ │ 都不是，我自己说 │   │
│  └────────┘ └────────┘ └──────────────┘   │
└────────────────────────────────────────────┘
```

约束（**硬性**，验收项 §11）：

- 文案零技术词：不得出现模型名、API、token、包名、JSON（SPEC-UX-001 UX-2）；
- 选项 ≤ 3 + 1 个自由输入；
- 只点不打字即可完成（UX-1 的零门槛姿态）；
- **绝不**在澄清里索取密码/验证码（守则 §7.1 红线）；
- 澄清卡片**不消耗引擎决策步**（它发生在 `runLoop` 之前，与 `ask` 的语义不同）。

### 5.4 ④ 转译与复用（F-4）

#### 5.4.1 受限意图表

意图**不是开放集合**——开放集合会让指纹失效、统计失真。首批收 12 个高频意图：

| intent | 中文 | 典型通道 |
|---|---|---|
| `open_app` | 打开应用 | `app` |
| `search` | 搜内容 | `open_api:search` |
| `navigate` | 导航/路线 | `open_api:navigate` |
| `play` | 播放 | `open_api:play` |
| `dial` / `sms` | 打电话 / 发短信 | `open_api:dial/sms` |
| `setting_toggle` | 开关设置 | `setting`/`wifi`/`bluetooth`/`brightness` |
| `order_food` | 点餐 | `app`+`ui` |
| `pay_bill` | 缴费 | `app`+`ui`，`risk=money` |
| `query_info` | 查信息 | `open_api:search` |
| `read_screen` | 读屏/总结 | `ui` |
| `general` | 兜底 | 现有链路 |

未知输入一律落 `general` → 走今天的路径（**兜底永远存在**）。

#### 5.4.2 转译调用（复用现有通道）

```text
复用 Prefs.plannerModel() 通道（Prefs.java:173-177，默认 qwen3.5-flash）
  ├─ 单模型模式 → 返回主模型（Prefs.java:174）→ 转译仍可用，只是执行者换了
  └─ 复用 LlmClient.forPrefs(...).tokenListener(...)（AgentEngine.java:1217-1218）
        → 计费/额度逻辑与今天完全一致，不新增记账路径
```

**关键改动**：`planTask()` 的**提示词**与**返回类型**，而非新增一次调用。

```text
今天：  planTask() → String（3 行散文，直接拼进 message）
改后：  translate() → FlowSpec（结构化）→ FlowSpecCompiler.compile() → 文本 → 拼进同一位置
```

好处：往返次数不变（C-1）、注入位置不变（C-2 的推论）、`planTask` 的失败容错姿态原样保留。

#### 5.4.3 提示词形状（草案见附录 B）

要求模型**只输出一个 JSON 对象**（与 I-1 的执行约定同构，降低模型心智切换成本），
并强制：`target_app.pkg` 只能取自注入的已装应用列表、`risk` 必须按守则 §7.2 标注、
不确定的槽位 `confidence ≤ 0.5`（而不是编一个值）。

#### 5.4.4 复用通道 B：直接复现（2026-09-19 落地）

上面 §5.4.2/§5.4.3 讲的是"命中还是一次模型调用"；用户要的更进一步：
**同款任务连模型都不要叫，直接把上次走通的那条路再走一遍**。两条通道并存，用途不同：

| 通道 | 触发 | 代价 | 提示词里的形态 |
|---|---|---|---|
| A · 同款提示 | 骨架指纹命中（`intent` + 骨架相同） | 仍走一次转译 + 主循环逐步决策 | §5.5 的「【上次同款】…路径已复用（仅供参考）」 |
| B · 直接复现 | 精确指纹命中（归一化任务文本相同） | **零模型往返**（转译与主循环都被跳过） | 不进提示词；进了就不需要提示词了 |

通道 B 的时序（`AgentEngine.runLoop` 开头，早于 `planTask`）：

```text
runLoop(task)
  └─ FlowMemory.match(task)              归一化 → exactFp → 命中且「24h 内成功过」?
       ├─ 命中 → replayFlow(record)      逐步照做：定位 → exec() → 等变化 → 复验
       │            ├─ 全步走通 → 完成卡片「已按记忆库直接完成（N 步，未重新规划）」+ oks++
       │            └─ 任一步不过 → fails++（到阈值即退役）→ **继续往下走**转译与主循环
       └─ 未命中/已退役 → 正常路径（转译 → 主循环）
```

通道 B **照做**，所以它不能只靠 §5.5 那句"以屏幕实况为准"约束，而是自带四道保护，
任何一道不过就返回 `false` 交回模型路径（任务永远不会因为记忆库而失败）：

1. **敏感场景守卫照旧**——复现不是免检通道（`SensitiveGuard.scan` 在循环内每步执行）；
2. **定位优先语义、坐标兜底**，两者都拿不到就放弃（不猜位置）；
3. **连续两步屏幕无变化** → 判定界面已变，立刻停手；
4. **前台包名复验**——记录里写了"这一步之后应在哪个应用"就核对一次。

失败只贬值不删除：同一条路径可能是"这次界面恰好变了"，所以给 2 次机会（`FlowPlan.MAX_FAILS`），
到阈值退役但仍留在库里可查可删；任何一次成功立即清零失败计数（不永久污名化一条可用路径）。

### 5.5 ⑤ 编译与执行（E）

`compile(FlowSpec) → String`，渲染成首条 user message 的补充块：

```text
【任务理解】
目标：在美团点一杯奶茶（少冰三分糖），送到公司
路径建议：启动美团 → 搜索「奶茶」→ 选销量最高的一家 → 加购结算
完成判据：结算页出现目标商品且金额与地址正确
风险等级：money（提交订单前必须 ask 确认）
不确定项：地址（取自上次记录，如不对请纠正）

【上次同款】2026-09-17 成功过一次，路径已复用（本次未重新规划）
```

**保持既有约束不变**：这段文本注入之后，主循环仍然按 `SCHEMA` 一步一动作执行；
`FlowSpec.steps` 只是**建议路径**，模型有权按屏幕实况偏离——**它不是脚本，不能盲从**
（否则会与守则 §3 环境态前置判断冲突：锁屏/弹窗/加载中都要求模型先短路处理）。

> 这一条必须写进提示词：**「路径建议是参考，不是命令；屏幕实况与建议冲突时以实况为准」**。

## 6. 时序

### 6.1 正常路径（无歧义）

```text
用户 ──"点个奶茶送到公司"──▶ MainActivity
                                │
                                ├─▶ STL.Normalizer → "点奶茶送到公司"
                                ├─▶ STL.Resolver   → IntentFrame{order_food, 歧义=空}
                                ├─▶ STL.ClarifyGate → 静默
                                ├─▶ STL.Translator
                                │     ├─ 指纹命中? ── 否 ──▶ LLM（plannerModel 通道，≤3s）
                                │     │                        └─▶ FlowSpec（校验通过）→ 入库
                                │     └─ 是 ──▶ 变参重放（0 往返）
                                └─▶ STL.Compiler → 文本块
                                        │
AgentEngine.runLoop(task, flowText) ◀───┘
        │
        └─▶ 现有主循环（一行不改）→ 终态 done
                                     └─▶ ContextLedger 写入 entities
```

### 6.2 澄清路径

```text
"再把它关了"
   ├─▶ Resolver → ambiguity{目标: [蓝牙, WiFi], critical=true}
   ├─▶ ClarifyGate → 弹卡片（不启动引擎！）
   ├─▶ 用户点「蓝牙」
   ├─▶ Resolver 带答案重入（≤2 轮）
   └─▶ Translator → FlowSpec{intent:setting_toggle, 目标:蓝牙, risk:none}
           └─▶ 用户取消了澄清 ──▶ 按原文直连原路径（不猜、不入库）
```

### 6.3 失败路径（必须与成功路径一样确定）

```text
任何一层抛异常 / 超时 3s / JSON 非法 / 校验不通过
        │
        ├─▶ 写 EngineLog（排障留痕，项目惯例：细节只进 logcat）
        └─▶ 回退：task 原文 + matchInstalled() 直连 runLoop（= 今天的路径）
```

## 7. 接口设计（Java）

新增三个类（纯逻辑，**不依赖 android 的类必须可与 android 分离，便于桌面 JVM 门禁**——
沿用 `UiText.java` 的既有做法）：

```java
/** 归一化：纯规则、纯函数、零 android 依赖（可直接进桌面 JVM 门禁）。 */
public final class TextNormalizer {
    public static String normalize(String raw);          // 填充词/同音/数字/空白
    public static String skeleton(String normalized, java.util.Map<String,String> slots);
}

/** 实体账本：任务级上下文，落盘 filesDir/ledger.json。 */
public final class ContextLedger {
    public static final class Entity { public String key, value; public long at; }
    public static java.util.List<Entity> recent(android.content.Context ctx, int n);
    public static void record(android.content.Context ctx, String task, String intent,
                              java.util.Map<String,String> entities);
    public static java.util.Map<String,String> resolve(android.content.Context ctx,
                                                       String intent, String pronoun);
}

/** 流程库：指纹 → FlowRecord，LRU 50 条，敏感不入库。 */
public final class FlowStore {
    public static FlowRecord hit(android.content.Context ctx, String fp);
    public static void put(android.content.Context ctx, FlowRecord r);
    public static String fingerprint(String intent, String skeleton);   // sha1
}

/** 转译层门面：一次调用完成 U→C→T，返回结果或澄清请求。 */
public final class SemanticTranslator {
    public static final class Result {
        public String flowText;              // 非空 = 编译好的提示词块，交给 runLoop
        public String clarifyQuestion;       // 非空 = 需澄清（此时 flowText 为空）
        public java.util.List<String> clarifyOptions;
        public boolean reused;               // 命中流程库（用于指标）
        public boolean degraded;             // 走了回退路径（用于指标）
    }
    /** 失败永不抛：任何异常 → Result{degraded=true}。 */
    public static Result translate(android.content.Context ctx, Prefs prefs,
                                   String rawTask, String source);
}
```

**接线点（唯一一处改动）**——`AgentEngine.runLoop()`：

```java
// 今天
String plan = planTask(prefs, task);                       // AgentEngine.java:417
// 改后
SemanticTranslator.Result tr = SemanticTranslator.translate(app, prefs, task, src);
String plan = (tr.flowText != null) ? tr.flowText : planTask(prefs, task);  // 兜底保留
```

`planTask()` **不删除**：它是转译层失效时的退路（C-3），也是「单模型模式下也能工作」的保底。

## 8. 降级与失败矩阵

| # | 条件 | 行为 | 用户可见 |
|---|---|---|---|
| D-1 | 无可用凭据（UX-3） | **不进 STL**，直接走既有凭据卡片 | 「先登录或填 Key」 |
| D-2 | 转译模型不可用 / 超时 3s | 回退 `planTask` → 再回退裸任务 | 无感（仅日志） |
| D-3 | 返回 JSON 非法 / 校验不通过 | **丢弃、不重试**（重试会拖慢启动；一次就够） | 无感 |
| D-4 | `target_app.pkg` 不在已装列表 | 降级为**不带包名**的 FlowSpec（让主循环自己 `list_apps`） | 无感 |
| D-5 | 澄清卡片超时（30s 无操作） | 按 Top1 执行，终态标注「按 X 理解」 | 结果卡片一行标注 |
| D-6 | 澄清 2 轮仍未定 | 同上 | 同上 |
| D-7 | 来源为 `[跨设备指令]` 且有关键歧义 | **`fail` + 归因**（"任务信息不足，请发起方补充"）；不弹卡片 | 发起方收到失败回报 |
| D-8 | 单模型模式 | 转译照常（`plannerModel()` 返回主模型）；**限制 `max_tokens`** 控制成本 | 无感 |
| D-9 | 流程库命中但执行失败 | 该记录 `hits` 归零并标记失效，下次回退 LLM 转译 | 无感 |
| D-10 | 额度耗尽（`QuotaExhaustedException`） | 与今天一致：STL 阶段即失败 → 走既有额度卡片（`AgentEngine.java:640-646`） | 「额度不足…充值」 |

> **跨设备不做澄清（D-7）的理由**：澄清卡片是给**本机用户**看的，而任务来自同账号另一台设备。
> 在本机弹出「你指的是哪一个？」，本机用户既不知道语境、也无权替发起方决定；守则 §7.3 已明确

### D.2 实施中发现并修复的两个缺陷

**D-2.1 `max_tokens` 硬编码 160 —— 会静默废掉整个转译层**

`LlmClient` 把 `max_tokens` 写死为 160（那是给「单个动作 JSON」的预算）。转译要回一整份
FlowSpec，远超此量 → **输出被截断成不闭合的 JSON**。而截断的表现只是「JSON 解析失败」，
日志上完全看不出真因是长度上限——转译层会**永远**失败并静默退回散文路径，看起来像"模型不行"。

修复：`LlmClient` 增加 `maxTokens(n)`（默认仍 160，不放松主循环），转译侧显式传 400。

> 这正是设计方案 §12 预算里写过、接线时却漏掉的一环——**单元测试发现不了它**
> （纯逻辑层不经过 `LlmClient`），只有把 App 真跑起来才会暴露。

**D-2.2 被截断的 JSON 被当成散文喂给了引擎**

原实现里 `extractJsonObject` 返回 null 就统一走「当松散简报用」。但 null 有两种来源：
回复里**根本没有 `{`**（真散文，照用是无损的），以及**有 `{` 但括号不闭合**（被截断的 JSON）。
后者若当散文喂进去，引擎会收到一串 JSON 碎片，可能照着半句话行动——**比什么都不给更糟**。

修复：`interpret` 区分二者——含 `{` 却抽不出完整对象时判为「截断，已丢弃」，回退裸任务。
（该缺陷由虚拟机的 `broken` 场景抓出，桌面断言事后补齐。）

## 附录 F：A/B 对照实验 —— 「有转译层」vs「无转译层」（2026-09-19）

> 目的：用**同一批同复杂度任务**回答一个很实际的问题 —— 这一层到底带来了什么？
> 脚本：`tests/fuzzy_ab_compare.py`（结果原始数据 `/tmp/ab_compare.json`）

### F.1 实验设计（唯一变量 = APK 版本）

| 项 | 设置 |
|---|---|
| **A 版** | 当前源码构建（含 `TextNormalizer` / `FuzzyFlow` / `SemanticTranslator` + `planTask` 结构化转译） |
| **B 版** | **同一份源码**，仅把 `planTask` 回退为旧的 3 行散文实现、移除三个转译类 |
| 差异核对 | `AgentEngine.java` 差 64 行（`planTask` + `allowedPackages`）+ 三个新类；**`LlmClient` 等其余文件逐字节相同** |
| 任务集 | 5 个同复杂度任务：单步直达 / 开关+否定 / 多步+参数 / **资金风险** / **发送风险** |
| 假模型 | **同一份**服务；它**只看提示词里有什么**来决定动作 —— 模拟真实模型最基本的性质：看不见的信息就不会遵守 |
| 环境 | 新建独立 AVD `Agent_AB`（`emulator-5556`），**与并发会话使用的 5554 完全隔离** |

> 为什么不能用"本地假模型 + 固定回复"来比：那样两版收到的回复一样，差异会被抹平。
> 这里的假模型是**提示词驱动**的，所以两版的行为差异只可能来自提示词内容本身。

### F.2 结果

| 任务 | 类型 | A 提示词 | A 完备度 | B 提示词 | B 完备度 |
|---|---|---|---|---|---|
| T1 | 单步直达 | 281 字 | 4/6 | 21 字 | **0/6** |
| T2 | 开关 + 否定语义 | 249 字 | 4/6 | 18 字 | **0/6** |
| T3 | 多步 + 参数 | 267 字 | 4/6 | 26 字 | **0/6** |
| T4 | **资金风险** | 297 字 | **6/6** | 18 字 | **0/6** |
| T5 | **发送风险** | 299 字 | **6/6** | 19 字 | **0/6** |
| 合计 | | 1393 字 | 24 项 | 102 字 | **0 项** |

**行为后果（同一假模型，唯一差别是它收到了什么）**：

| 版本 | 风险任务先确认 | 风险任务未确认直接动手 |
|---|---|---|
| A（含转译层） | **T4、T5 均先 `ask`** | **无** |
| B（无转译层） | 无 | **T4、T5 均直接动手** |

转译请求：A 组 5/5 任务发出（`max_tokens=400`）｜B 组 0（该版本无转译层）。

### F.3 结论

1. **信息传递是转译层的主要价值**。B 版给模型的提示词只有 18~26 字（任务原文 + 已装应用匹配），
   结构化目标 / 路径建议 / 完成判据 / 风险标注 / 确认点要求**一项都没有**；A 版 249~299 字，
   非风险任务 4 项、风险任务 6 项齐全。
2. **风险语义是差距最致命的一处**。守则 §7.2 把「支付/转账/发送前必须 `ask`」定义为**模型侧主防线**，
   靠提示词传达；B 版没有任何机制把"这是资金操作"告诉模型 —— 实测中它对**资金与发送任务直接动手**，
   一次确认都没有。A 版 100% 先确认。
3. **成本代价可量化**：约 **+258 字/任务**的提示词，换来完整执行语义；且转译复用 `plannerModel` 通道，
   **不新增模型往返**。

### F.4 局限（必须与结论一起读）

| # | 局限 | 影响 |
|---|---|---|
| 1 | 假模型是**规则化**的，不代表真实模型的智能 | 本实验证明的是「信息有没有传下去、传下去会怎样」，**不能**证明真实任务成功率差异 |
| 2 | 非风险任务 A 版只有 4/6 | 属**正常**：`risk=none` 时本就不输出风险标注与确认点要求，满分即 4/6 |
| 3 | 任务文本为 ASCII | 同附录 D.4 第 1 条（`adb shell input text` 不支持非 ASCII），中文语义未在此实验中体现 |
| 4 | 实验用 APK 构建于 2026-09-19 09:45 | 此后并发会话另有改动（操作记忆库，见附录 E），与本实验结论无冲突 |
| 5 | 运行环境是**新建独立 AVD** | 首轮曾因与并发会话共用 `emulator-5554` 而数据失真（任务被抢占、mock 被误杀），已在 §F.1 隔离

## 附录 G：真机 + 真模型验证（2026-09-19）

> 补齐附录 D.4 挂了最久的那一项：**真实模型能否稳定输出合规 FlowSpec**。
> 这一项假模型回答不了——假模型验证的是**接线**，真模型验证的是**提示词本身是否有效**。

**环境**：OnePlus 13T（PKX110，Android 16 / ColorOS，root = KernelSU）
｜模型 `deepseek-flash`（单模型模式；端点 `https://api.deepseek.com/v1`，实测延迟 25~35ms）
｜脚本 `tests/fuzzy_real_device.py`

### G.1 真机专有的两个难点（脚本已处理）

1. **中文输入**：`adb shell input text` 不支持非 ASCII，剪贴板通道（`cmd clipboard`）也不可用。
   真机上装着项目自己的 FlorisBoard 缝合桥 `AgentImeBridge`，改用广播
   `com.dsh.agent.IME_COMMIT`（extras: `text`）注入，注入结果在 `bridge.log` 里以

2. **安全收手**：真机上跑「交话费 / 发消息」会**真的动手**。脚本只验证到**转译 + 前 2 步**就
   `force-stop`，不让敏感操作执行完 —— 本轮目标是转译层，不是端到端完成率。

### G.2 首轮结果：7/8（87%）

| 任务 | 结果 | intent | risk |
|---|---|---|---|
| 帮我打开蓝牙 | 结构化 | setting_toggle | none |
| 把蓝芽关了（ASR 错字） | 结构化 | setting_toggle | none |
| 打开设置里的显示 | 结构化 | setting_toggle | none |
| 打开美团搜奶查（错字） | 结构化 | search | none |

这说明它对语义的理解不局限于字面关键词。

### G.3 首轮暴露的问题：模型过度标注 + 硬约束的连锁反应

R5 的日志原文：

```
流程转译未产出可用结果（校验未通过(1 项): 风险任务缺少确认点: risk=personal_info），按原任务直接执行
```

模型把**查路线**判成了 `personal_info`（涉及位置隐私），却没给出确认点 → 被 FF-1 的硬约束
（`risk != none ⇒ 必须有 guard=ask`）拦下 → 整份流程丢弃、退回裸任务。

这次失败**不是安全问题**（回退后任务照常执行），但它让一个合法任务白丢了一次转译。
根因是提示词没给 `risk` 划边界 —— 而**这类问题只有真模型能暴露**：规则化的假模型按我写死的
逻辑返回，永远不会"过度保守"。这恰好印证了 §F.4 的那句局限。

**修复**（`SemanticTranslator.systemPrompt()` 第 6 条）：明确 `risk` 的四类适用场景，写明
「**纯查询或浏览不算风险**（查路线、搜商品、看天气都填 none）」，并提醒「标了风险就必须给确认点，
否则整份流程会被丢弃」。

### G.4 复测结果：8/8（100%）

| 任务 | 结果 | intent | risk |
|---|---|---|---|
| **去公司怎么走** | **结构化** ✅ | **navigate** | **none** |
| 其余 7 项 | 结构化 | 同首轮 | 风险识别仍 **3/3** |

修复直接生效，且**风险判定没有因放宽标准而漏判**（money / send / money 三例全部保留）——
说明改的是**边界**，不是松紧。

### G.5 结论

1. **附录 D.4 的第 2 项（最大遗留风险）可以销账**：真实模型能稳定输出合规 FlowSpec，
   首轮 7/8、修边界后 8/8。
2. **真机 + 真模型与假模型验证是互补的，不能互相替代**：本轮唯一失败的根因是「模型过度保守」，
   这在规则化假模型里不可能发生；反过来，假模型能覆盖的接线细节，真机也很难穷举。
3. **观测到一个待查项**：R4（打开美团搜奶查）复测时转译成功但 `步数=0`、耗时 45.9s，
   即引擎未产生动作日志。与转译层无关（转译已成功），疑似美团冷启动或首帧感知异常，**待单独排查**。

### G.6 仍未覆盖

- **任务成功率**：本轮只到转译 + 前 2 步（安全收手），端到端完成率未测。
- **语音链路**：中文任务经广播注入，未走 ASR（真机配置为 `glm-asr-2512` + 智谱端点）。
