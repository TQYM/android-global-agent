# 客户端字体可读性检测报告

> 对象：`agent-unified/dist/agentlite-unified-0.7.0-android.apk`（客户端 0.6.0）
> 实测环境：Android 14（API 34）模拟器，1080×2400 @420dpi，系统字体缩放 1.0–2.0×
> 日期：2026-09-12

检测围绕**字体**这一条主线：字号够不够、会不会随系统字体缩放、放大后装不装得下、
字重与行距是否成立、文字与底色是否还看得清。

---

## 1. 结论

| 级别 | 发现 | 证据 |
|---|---|---|
| **P1** | **×2.0 时 3 个控件裁字**：28dp 固定高度的 `btnResetTokens`/`btnDisplayCalib`/`btnDisplayRefresh`（11sp）需要 78px 行高，容器只有 74px | 实测 ×2.0；静态模型独立预测 ≥1.82×，两者吻合 |
| **P1** | **输入框提示文字对比度不足**：默认 3.63:1、动态取色实测 **2.03:1**（正文需 4.5:1） | 静态 + 像素实测 |
| **P2** | **手表页字号偏小**：23 处 < 12sp，最小 **9sp**（穿戴建议 ≥ 12sp） | 静态普查 |
| **P2** | **全 App 43 处声明 < 12sp**（9sp×2、10sp×9 全在手表页；11sp×32 手机与手表都有）；手机页渲染后 14 个控件 < 12sp | 静态普查 + 实测 |
| **P3** | `sans-serif-medium` 用在 6 处中文标签上——CJK 会回退常规字重，声明的强调很可能不生效 | 静态 |
| **P3** | 中文多行段落仅 2 处设了 `lineSpacingMultiplier=1.2`，其余为默认紧行距 | 静态 |
| ✅ | **全部字号都用 sp**：139 处 textSize 无一使用 dp/px，系统字体缩放能正常生效 | 静态普查 |
| ✅ | **×1.0–×1.8 全程无裁字**；×2.0 另有 13 个控件余量仅 3%–14%（临界） | 字体缩放压测 |
| ✅ | 无硬切/截断；正文与按钮对比度实测最低 4.81:1，达标 | 实测各页 |

## 2. 字体缩放压测（主证据）

`tests/font_scale_sweep.sh` 在 6 个字体档位（1.0/1.15/1.3/1.5/1.8/2.0）下重走
登录 → 主界面 → 设置页（含滚到底部），逐档截图并取控件树；`tests/font_scale_readability.py`
按「需要行高 = 声明 sp × 缩放 × 密度 × 中文行高系数」与**实测控件框高**比对。

| 档位 | 可评估控件 | 裁字 | 临界（余量 < 18%） |
|---|---|---|---|
| ×1.0 | 37 | 0 | 0 |
| ×1.15 | 37 | 0 | 0 |
| ×1.3 | 34 | 0 | 0 |
| ×1.5 | 34 | 0 | 1 |
| ×1.8 | 38 | 0 | 8 |
| **×2.0** | 34 | **3**（3 个 28dp 按钮） | **13** |

×2.0 下余量最紧的几个：`btnConfig`、`btnA11yBanner`（103%）、`btnBack`（103%）、
`tvSyncHint`/`btnA11y`/`btnAutoStart`（108%）、`btnRefreshQuota`/`btnLogout`（112%）、
`etRedeem`/`btnRedeem`（114%）。

**为什么偏偏是那 3 个**：它们是全 App 唯一「28dp 固定高度 + 11sp 文字」的组合——
11sp × 2.0 × 2.625(密度) × 1.35(行高) = 78px > 28dp = 74px。其余按钮高 32–48dp，同档仍装得下。

**两条独立路径互相验证**：纯静态模型（只读 APK 资源，不看设备）预测「这 3 个在 ≥1.82× 裁字」，
压测结果 1.8× 通过、2.0× 失败——吻合。

## 3. 字号普查

139 处 `textSize` 声明，**全部为 sp**（无 dp/px，这点是对的）：

| 字号 | 处数 | 评价 |
|---|---|---|
| 9sp | 2 | 手表页；穿戴建议 ≥ 12sp |
| 10sp | 9 | 手表页 |
| 11sp | 32 | 手机+手表辅助文案；低于 Material body-small(12sp) |
| **12sp** | **48** | 主力正文尺寸 ✅ |
| 13sp | 32 | 按钮/强调 ✅ |
| 14–16sp | 13 | 标题/输入 |
| 20sp | 3 | 页面大标题 |

手机页渲染后 < 12sp 的控件 14 个；手表页 23 个。

## 4. 字重与行距

- `android:fontFamily="sans-serif-medium"`（6 处）：中文没有对应 medium 字重，实际回退常规字重
  → 这 6 处想要的「加粗强调」在中文上消失。要强调应显式 `android:textStyle="bold"`，
  或改用不依赖字重的区分手段。
- `lineSpacingMultiplier="1.2"` 只出现在 2 处；中文多行段落（登录页规则说明、引导弹窗）
  用系统默认紧行距，长段落阅读偏累。建议正文类多行文本统一 1.2–1.35。

---

## 5. 文字对比度（字看得清不清）

- 正文/按钮：静态 138 组最低 4.82:1，实测各页最低 4.81:1 ✅
- **输入框提示文字**：`color_text_hint`(#8E8A94) 压在 `color_surface_container_highest` 上，
  默认 3.63:1；Material You 动态取色把输入框填充调亮后实测 **2.03:1**（AA 正文需 4.5:1）。
  受影响：下达指令、兑换码、语音模型、同步服务器地址等所有输入框提示。
  修法：`color_text_hint` 改用 `color_on_surface_variant`（约 7:1），一处改动全局生效。

## 6. 复现

```bash
# ① 静态（无需设备）：字号/单位/固定高度/字重/行距 + 提示色对比度
python3 tests/apk_readability.py path/to/app.apk

# ② 字体缩放压测（需设备或模拟器）
bash tests/font_scale_sweep.sh <serial> /tmp/fontscale     # 取样：6 档 × 各页面
python3 tests/font_scale_readability.py /tmp/fontscale     # 分析：裁字 / 临界

# ③ 真实渲染的文字对比度（需截图 + 控件树）
python3 tests/ui_render_readability.py /tmp/fontscale/2.0/settings
```

## 7. 方法上的自我修正（避免后人重踩）

字体度量最容易得出「看着像真的」的错结论。开发本工具时修正过 5 处：

| 误报/失真 | 根因 | 修正 |
|---|---|---|
| 按钮对比度 1.24:1 | 拿 `on_primary` 比祖先 surface，忽略 M3 样式提供的填充 | 按 `on_X` ↔ `X` 配对语义判定 |
| 按钮对比度 1.83:1 | 采样框含按钮圆角外的卡片底色 | 采样收窄到文字所在中心区 |
| 控件 id 与文字错配 | uiautomator 属性顺序不固定，固定顺序正则错配 | 整标签取属性 |
| 「达成率恒为 1/缩放」 | 墨迹量到的是填充区与圆角混色，不是字形 | **放弃墨迹法**，改用「声明 sp × 缩放 vs 实测框高」的确定性模型 |
| 3 个 28dp 按钮漏检 | 同名 id 在手机(28dp)/手表(42dp) 两套布局声明不同，按 id 建表被覆盖；且被 ScrollView 裁过 | 声明度量按**布局文件+id**索引；只评估完整可见的观测（取样额外滚到底部） |

> 结论：字体度量不适合以像素取证为主依据（字形墨迹会被填充、圆角混色、下划线污染），
> 「声明值 + 实测框高」这两个可复核量已经足够回答问题。
